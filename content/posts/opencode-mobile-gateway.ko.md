애들 키우면서 사이드 프로젝트를 굴리는 건 시간 문제가 아니라 *집중 시간*의 문제다. 한 시간 딱 앉아서 코딩할 수 있는 날이 일주일에 몇 번이나 될까. 에이전틱 코딩은 그 귀한 한 시간을 더 쓸 수 있게 해줬다.

문제는 그 한 시간이 노트북 앞이 아니라는 점이었다.

TUI를 모바일에서 쓰는 건 고통이다. 스크롤은 끊기고, 긴 출력은 추적하기 어렵고, `SIGKILL` 한 방에 컨텍스트가 증발한다. 그래서 텔레그램을 OpenCode의 인터페이스로 쓰는 게이트웨이를 만들기로 했다. 메시지 하나 보내면 로컬에서 `opencode run`이 돌고, 결과가 다시 텔레그램으로 온다. 단순한 구조다.

그래서 만든 게 **hermux**다. 텔레그램을 OpenCode의 프론트엔드로 쓰는 경량 게이트웨이.

지금 할 수 있는 건 이 정도다:
- `/repos`로 연결 가능한 프로젝트 목록 확인
- `/connect <repo>`로 현재 채팅을 특정 repo에 바인딩
- 메시지 하나 보내면 `opencode run`이 돌고, 결과가 Markdown으로 정리돼서 돌아온다
- `/session`으로 현재 세션 확인, `/reset`으로 초기화
- 대화 맥락이 유지되니까 "아까 그 파일"이 통한다

내부적으로는 `--format json`으로 이벤트 스트림을 받아서 `step_start`, `step_finish`, `tool_use` 같은 단계별로 파싱하고, `md2html`로 텔레그램용 메시지를 변환한다. 길이 제한 분할도 처리해서 긴 출력도 끊기지 않는다.

OpenClaw의 게이트웨이 패턴을 포크해서 스캐폴딩했고, 여기까지는 평범한 개발이었다.

진짜 문제는 그 다음이었다.

## 자기 자신을 수정하면 죽는다

이 프록시는 자기 자신의 소스 코드를 수정하는 용도로도 쓰인다. 모바일에서 텔레그램으로 명령을 보내고, 에이전트가 `gateway.js`나 `runner.js`를 고치고, 그러면 돌아가던 데몬이 죽는다. 재시작. 또 수정. 또 죽음. 이 루프가 계속 반복됐다.

게다가 Telegram은 동일 토큰으로 폴링하는 데몬이 두 개 이상 뜨면 `ETelegram` 충돌을 뿜는다. MVP 버전과 개발 버전이 뒤섞여 돌아가면서 뭐가 어디서 죽었는지 파악하기도 힘들어졌다.

처음엔 코드 버그를 의심했는데, 원인은 더 단순했다. **"자기 자신을 개발하는 런타임"과 "테스트 대상"이 분리되어 있지 않으면 운영이 불안정해진다.** 실행권을 잃으면 기능이 아무리 많아도 소용없다.

## FIX / DEV / HELLO: 세 개로 쪼개면 살아남는다

결국 구조를 세 겹으로 나눴다.

- **FIX**: 개발 도구. DEV를 수정할 때 쓰는 안정된 에이전트. 얘가 죽으면 개발 자체가 멈추니까 최대한 안 건드린다.
- **DEV**: 개발 대상. 실제로 기능을 붙이고 실험하는 본체. 깨져도 된다, FIX가 살아있으니까.
- **HELLO**: 테스트용 최소 repo. 도메인 복잡도 없이 라우팅/세션/입출력만 검증한다.

핵심은 **"자기 자신을 개발하는 에이전트"와 "개발당하는 에이전트"를 분리**한 거다.

실제로는 이렇게 정리됐다.

`my-dev-bot`(FIX)이 `@hermux/cli`(DEV)를 개발한다. 각각 별도 Telegram 토큰, 별도 repo, 별도 workdir. `chatId`는 repo 하나에 하나만 매핑되고, 중복은 fail-fast로 막는다.

```
my-dev-bot (FIX = 개발 도구)
├── 토큰: 별도
├── repo: @hermux/cli ← 여기를 수정함
└── workdir: ~/.openclaw/workspace/@hermux/cli

hermux (DEV = 개발 대상, 검증용)
├── 토큰: 별도
├── repo: hello-world-repo
└── workdir: ~/.openclaw/workspace/hello-world-repo
```

이 분리 이후부터 흐름이 매끄러워졌다. FIX로 DEV를 수정하고, DEV는 HELLO에 붙여서 검증한다. FIX가 살아있는 한 개발은 멈추지 않는다.

## 세션이 없으면 대화가 아니다

구조를 나눠도 사용자 경험을 망치는 게 하나 남아 있었다. "이 키워드 기억해"라고 했는데 다음 턴에서 까먹는 문제.

원인은 단순했다. 매 메시지를 단발 실행(stateless)으로 처리하고 있었다. chat+repo 기준으로 session map을 도입하고, session id를 저장·재사용하게 바꿨다. `/session`으로 확인하고 `/reset`으로 초기화한다.

이게 들어간 뒤에야 비로소 **"모바일 OpenCode 인터페이스"** 느낌이 났다.

## OpenClaw는 복구 레이어였다

초기 개발 단계에서 OpenClaw는 보조 도구가 아니었다. 프록시가 자기 소스를 건드리다 죽을 때마다 OpenClaw가 재기동하고, 설정을 교정하고, 로그를 확인하고, 작업 컨텍스트를 이어줬다. 일종의 **운영 복구 레이어**였다.

흐름을 정리하면 이렇다:
1. OpenClaw의 게이트웨이 패턴으로 스캐폴딩
2. 프록시가 자기 자신을 개발하면서 반복적으로 죽음
3. OpenClaw로 불안정 구간을 살려냄
4. FIX/DEV/HELLO 분리로 안정화

결국 "OpenCode 모바일 프록시"를 만든 게 아니라, **끊기지 않는 개발 루프를 설계한** 거였다.

## 운영 검증은 세 줄이면 된다

```bash
ls runtime/gateway.pid          # 1. PID 파일 존재?
tail runtime/gateway.log        # 2. 로그에 에러?
ps aux | grep gateway           # 3. 프로세스 살아있나?
```

성공 신호: `polling with 1 bot for 1 repo(s), 1 chat id(s)`
문제 신호: `ETelegram` 반복 → 동일 토큰 다중 실행 의심 → 코드보다 먼저 데몬/설정 정리

## 다음 단계

지금은 "돌아간다" 수준이다. 매일 쓰는 도구로 굳히려면 몇 가지가 더 필요하다.

- **자동 복구**: `SIGKILL` 당해도 supervisor가 알아서 살려주는 구조
- **상태 표시**: run / idle / timeout / error를 채팅에서 바로 확인
- **메신저 확장**: 텔레그램 말고 Discord, Slack 어댑터
- **CLI 통합**: 여러 에이전트를 하나의 인터페이스로 오케스트레이션
- **전용 클라이언트**: 언젠가는 텔레그램도 벗어나서 네이티브 앱으로

일단 오늘은 "죽지 않고 돌아가는 구조"까지 왔다. 나머지는 차근차근.

## 결론

이번 작업에서 기능 구현보다 더 많은 시간이 들어간 건 운영 설계였다.

처음엔 "텔레그램으로 OpenCode 쓰기"가 목표였는데, 끝나고 보니 핵심 질문은 이거였다: **모바일 제약 환경에서 끊기지 않는 개발 루프를 어떻게 만들 것인가.**

정답은 분리였다. 자기 자신을 개발하는 런타임과 테스트 대상을 쪼개고, 각각 독립된 토큰과 경로를 주고, 죽으면 복구할 수 있는 기준선을 유지한다.

하루 종일 노트북 앞에 앉아 있지 못해도 괜찮다. **한 시간짜리 집중 안에서 프롬프트 하나가 쌓이면, 루프는 계속 돈다.**
