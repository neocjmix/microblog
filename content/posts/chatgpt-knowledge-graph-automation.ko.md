대화가 쌓이면 기록은 되는데, 나중에 다시 찾기는 어려워진다.  
이번 작업의 목표는 단순 보관이 아니라 **대화를 재사용 가능한 지식으로 바꾸는 것**이었다.

핵심 질문은 세 가지였다.

1. 수천 개 대화를 어떻게 자동 분류할까?
2. 서로 관련 있는 대화를 어떻게 연결할까?
3. 이 과정을 사람이 검증 가능한 방식으로 만들 수 있을까?

---

## 문제 정의: 파일은 많은데 탐색 경로가 없다

대상은 Obsidian에 쌓인 ChatGPT 대화 markdown 3,263개.

- 폴더 재구성은 하지 않기
- 시간순 흐름은 유지
- 태그와 문서 간 링크로 탐색성 높이기

즉, 구조를 갈아엎는 대신 **메타데이터(태그/연결)** 를 강화하는 전략이었다.

## 1) 태깅 파이프라인: LLM과 스크립트의 역할 분리

초기 요구는 이랬다.

- 제목+본문 전체 스캔
- 태그 후보를 폭넓게 추출
- 문서별 멀티 태깅
- 과태깅/과소태깅을 피하도록 가중치 조정

### LLM이 맡은 영역 (정책 설계)

LLM은 대량 파일을 직접 태깅하지 않고, 다음을 설계했다.

- 태그 체계 초안 (`dev/frontend`, `health/medical` 같은 계층형)
- 키워드 사전 설계 방향 (high/medium 우선순위)
- 임계값/가중치 실험 방식
- 품질 점검 기준(과태깅/과소태깅)

### 스크립트가 맡은 영역 (반복 실행)

대량 처리와 재현성은 스크립트로 고정했다.

#### `extract-keywords.py`

- 제목/본문에서 토큰 추출
  - 한글: 2글자 이상
  - 영문: 3글자 이상
- 불용어 제거
- 문서별/전체 빈도 집계
- `_keyword_analysis.json` 산출

#### `apply-tags.py`

핵심 점수 로직:

1. `TAG_KEYWORDS` 사전 매칭
   - high 키워드 가중치 2
   - medium 키워드 가중치 1
2. 제목 가중 반영
   - `score += weight * 3`
3. 본문 과반영 방지
   - 출현 횟수 `min(count, 5)` 캡
   - `score += weight * count * 0.5`
4. 태그 채택
   - `min_score = 3.0`
   - 상위 `max_tags = 5`
5. frontmatter 업데이트
   - `chatgpt`, `conversation` 유지
   - 포맷 보존 + retry

핵심은 모델의 순간 판단보다, **일관된 점수 규칙으로 대량 문서를 안정 처리**한 점이다.

### 실제 모바일 확인

데스크톱 로그뿐 아니라 Obsidian 모바일에서 properties 렌더링을 확인했다.

![Obsidian 모바일 frontmatter 태그 확인](/images/posts/2026-02-14/chatgpt-tagging-mobile-check.jpg)

이 검증이 중요한 이유:

- YAML이 맞는지뿐 아니라 UI에서 정상 표시되는지 확인 가능
- 멀티태그가 실제 검색/필터에서 usable한지 확인 가능
- 과태깅 케이스를 사람 검토로 후속 튜닝 가능

## 2) 문서 연결: raw overlap → TF-IDF

초기엔 키워드 겹침(raw overlap)으로 유사도를 계산했는데 품질 문제가 컸다.

- 흔한 단어 때문에 무관한 문서 연결(false positive)
- 링크 수는 많지만 의미가 약한 그래프

### TF-IDF가 해결한 문제

TF-IDF는

- 특정 문서에서 중요한 단어는 강조
- 전체 문서에서 흔한 단어는 약화

하는 방식이다.

여기에 불용어 필터와 코사인 유사도를 결합해 더 의미 있는 연결을 만들었다.

---

## 3) Human-in-the-loop: 임계값은 사람이 확정

자동화에서 제일 중요한 건 사람이 품질을 고정할 수 있어야 한다는 점이다.

유사도 threshold는 자동 확정하지 않고, 사람이 샘플을 검토해 결정했다.

검증 과정:

1. 임계값별 링크 밀도 통계 비교 (0.10/0.15/0.20)
2. 대표 문서 샘플링 후 연결 품질 육안 검토
3. 노이즈와 커버리지를 동시에 보는 균형점 선택

그 결과 `threshold=0.15`, 문서당 최대 링크 제한(`max 10`)으로 확정했다.

즉 이번 파이프라인은
**자동 생성 → 인간 검토 → 기준 고정** 구조로 작동했다.

## 4) 운영에서 실제로 막힌 지점

알고리즘보다 운영 환경 이슈가 더 컸다.

### iCloud dataless

일부 파일이 로컬에 실제 데이터가 없는 상태라 읽기 실패가 발생했다.  
코드 문제가 아니라 스토리지 상태 문제였다.

### macOS 권한/실행 컨텍스트

같은 명령도 iTerm/peekaboo/node 중 누가 실행하느냐에 따라 결과가 달랐다.  
자동화에서는 기능 구현만큼 **실행 컨텍스트 설계**가 중요하다는 걸 확인했다.
